# 과제 8 — 통과 기준 확인/증거 수집 계획

> **먼저 알려드릴 점**: 이 대화 중간에 컨텍스트가 한 번 정리(compaction)되면서, 원래 붙여넣어
> 주셨던 카드 1~5의 T08-C01~C53 문항 원문 전체가 지금 제 쪽에는 남아있지 않습니다. 요약본에는
> 일부 문항 번호(C14, C15, C17, C25, C27, C28, C31, C33, C36~C41, C46 등)와 각 카드의
> 취지만 남아있어서, 아래 계획은 **그 요약과 실제 구현 코드를 근거로 다시 구성한 것**입니다.
> 번호를 정확히 1:1로 맞추고 싶으시면 원래 카드 원문을 다시 붙여주시면 그 자리에서 문항별로
> 재배열해 드리겠습니다. 다만 아래 표만으로도 5개 카드가 요구한 내용은 빠짐없이 다룹니다.

이 문서는 "무엇을 확인해야 하는지"와 "그걸 어떻게 캡처해서 증거로 남길지"를 미리 정리한
**계획**입니다. 실제 캡처 결과(스크린샷, `#evidenceLog` 내용)는 배포 후 직접 진행하면서
`[ ]`로 표시된 자리에 채워 넣으시면 됩니다. AI가 실행 결과를 미리 지어내지 않습니다 —
실제로 브라우저에서 눌러보고 나온 값만 채워야 증거로서 의미가 있습니다.

## 인증 구현 설명서 초안 골격 (6항목)

아래는 실제 캡처 결과를 채워 넣을 수 있도록 만든 골격입니다. `[ ]`를 실제 값/캡처로 교체하세요.

1. **무엇으로 구현했는가**: WebAuthn(패스키) 표준 + Supabase Edge Function(Deno) + `@simplewebauthn/server` v11(서버 검증 라이브러리) + Postgres(RLS 적용) + Supabase Auth(세션 토큰 발급용). 비밀번호/OTP 화면은 전혀 사용하지 않음.
2. **왜 이 방식인가**: Supabase가 제공하는 네이티브 패스키 베타 기능도 검토했으나, 등록/로그인/삭제/격리 검증에 필요한 세부 동작(챌린지 저장 위치, 재사용 거절, 계정별 자격증명 구분)을 과제 채점 기준에 맞춰 직접 통제하기 위해 커스텀 Edge Function 방식을 선택함.
3. **소스에서 무엇을 바꿨는가 (4개 흐름 전부)**:
   - 등록: `passkey-register-start` + `passkey-register-verify` (신규)
   - 로그인: `passkey-login-start` + `passkey-login-verify` (신규)
   - 로그아웃: 프론트 `sb.auth.signOut({scope:"global"})` 호출부 (신규), 서버 쪽은 Supabase Auth가 세션을 즉시 무효화
   - 비공개 자료 조회: `private-notes` Edge Function (신규), `index.html`에 `#private` 섹션/JS 추가
4. **네거티브 케이스 4종 기록**: [ ] 카드5 표의 캡처 결과를 여기에 정리해서 채움 (성공/거절 쌍으로)
5. **AI와 나의 판단 분담**: [ ] 아래 "AI와 내 판단" 3줄 참고해서 서술형으로 확장
6. **아직 방어하지 못한 것 (최소 1개, 구체적으로)**: 예시 후보 — "브라우저 저장소(로컬스토리지/세션)에 저장된 `access_token`/`refresh_token`을 탈취하는 XSS류 공격에는 별도 방어가 없음(예: CSP 미설정)". 실제 구현을 다시 훑어보고 본인이 확인한 구체적인 미방어 지점으로 교체할 것 — 빈 칸/추상적 답변은 통과하지 못함.
